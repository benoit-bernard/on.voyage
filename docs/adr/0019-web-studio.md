# ADR-0019 — Espace créateur `Web.Studio` (T-1206)

- Statut : accepté — MVP. Hors périmètre de cette tranche : connexions Instagram et YouTube (ADR-0020), géo-association (ADR-0021), listes et itinéraires, statistiques, modération avec contestation, partage.

## Choix
- **`OnVoyage.Web.Studio`** : Blazor Web App en rendu interactif serveur, construit comme `Web.Admin` (ADR-0009) : ni base, ni code métier, ni secret ; il parle au **Gateway** avec le jeton du créateur (`IStudioApi`), les modèles sont les DTO de `Creators.Contracts`. Les pages d'inscription et de connexion sont des formulaires HTML classiques. Le code est **dupliqué** (jeton, session, connexion) plutôt que partagé avec `Web.Admin` : deux hôtes de quelques centaines de lignes, aucune bibliothèque commune justifiée, et le jour où l'un évolue (OAuth, cookies) l'autre n'est pas touché. Entrée dans la solution, l'AppHost (`web-studio`), `docker-compose.yml`, `Caddyfile` (`studio.<domaine>`), la surveillance et la matrice de construction.
- **Connexion** : le même code à six chiffres que les voyageurs (Platform, ADR-0005) ; cookie `ov_studio` (`HttpOnly`, `SameSite=Strict`) avec un identifiant de session opaque. Contrairement à `Web.Admin`, **les rôles ne sont pas figés dans le cookie** : à chaque requête, `OnValidatePrincipal` relit les rôles de la session gardée côté serveur. Platform donne `creator` un instant après `CreatorTermsAcceptedV1` (file Wolverine) : l'inscription demande donc une session renouvelée (`IRoleRefresher`, 6 essais à 700 ms) jusqu'à voir le rôle, puis recharge la page avec le nouveau principal. Si le rôle n'est pas arrivé, la page le dit et le bouton « Ouvrir mon espace » réessaie.
- **Contrôle d'accès à trois niveaux** (SEC-03) : `StudioGate` répond **403** (journalisé) à tout compte connecté sans `creator` sur `/studio/*`, sauf `/studio` et `/studio/join` (les deux portes qui existent avant le rôle) ; les pages portent `[Authorize(Policy = "creator")]` ; le Gateway route `/api/creators/v1/studio/{registration|signup|terms}` en politique `account` (e-mail vérifié : une session anonyme ne devient pas créateur) et le reste de `/studio/**` en politique `creator`, et **le service refuse lui-même** un jeton sans rôle.
- **Le créateur est le compte du jeton.** Aucune route du Studio ne porte d'identifiant de créateur : `StudioHandler` retrouve le créateur par `account_id` et délègue aux gestionnaires existants (`CreatorAdminHandler`, `CreatorContentHandler`) avec ses identifiants. Ainsi une règle (handle, publication F-26, chapitres, 280 caractères, événements `CreatorPlaceLinkChangedV1`…) n'existe qu'une fois. Conséquence : une écriture du créateur produit aussi une entrée du journal Platform (`AdminActionRecordedV1`, acteur = compte du créateur, action `creator.update`, `tip.set`…). C'est voulu (traçabilité DSA des modifications) mais le journal « admin » mêle désormais les deux ; l'écran Journal filtre par acteur.
- **Inscription** (`POST /studio/signup`) : crée le brouillon (`founding = false`) **et** enregistre l'acceptation des CGU dans la même transaction, avec `CreatorTermsAcceptedV1`. La version acceptée doit être la version courante (`Creators:Terms:CurrentVersion`, défaut `2026-10`) ; une version périmée est refusée (`terms_required`). Un fondateur (consentement signé, `terms_version = fondateur`) qui se connecte avec le compte rattaché est reconnu et peut accepter les CGU (`POST /studio/terms`) : il garde `founding = true`, la référence du document signé est alors remplacée par l'acceptation.
- **Publication par le créateur** : seulement quand `PublishBlock` est vide (CGU, une spécialité). Un créateur **suspendu** lit mais n'écrit pas (403 `creator_suspended`) et ne peut pas lever sa suspension : seul l'administrateur le fait. Le handle d'un profil publié ne change pas (`handle_locked`) : il est dans les liens partagés, l'app et les moteurs de recherche.
- **Abonnés** : l'espace n'affiche qu'« Nouveau créateur » sous 20 puis le nombre ; aucune liste, aucun identifiant (test d'intégration). Même règle que la page publique.

## Écarts et limites
- **Texte des CGU** : le texte juridique est la tâche humaine H-010. L'écran d'inscription affiche une **synthèse des engagements** tirée du cahier (licence d'affichage des vignettes, transparence commerciale, sites fragiles, modération, abonnés jamais communiqués, sortie) avec la mention « Texte provisoire » ; la version est celle du serveur. À remplacer avant l'ouverture publique (`docs/questions/Q-2026-10-02-cgu-createurs.md`).
- **Textes d'interface** en français dans le code (`Text/Labels.cs`, pages), comme `Web.Admin` : les ressources FR/EN de la règle copilot-instructions ne sont pas encore en place sur les hôtes serveur.
- **Aucun import** à cette tranche : la connexion Instagram/YouTube et la géo-association viennent ensuite. Le Studio gère les contenus par URL (alternative toujours disponible, F-27).
- **Photo** : le profil enregistre un chemin ; le téléversement d'une photo n'existe pas (Admin non plus).
- **Déploiement** : `creators-api` n'est pas encore dans `docker-compose.yml` (ADR-0016) ; l'espace créateur y est déclaré mais inutilisable tant que ce service n'y est pas.
- **Sessions en mémoire** : un redémarrage de `web-studio` déconnecte les créateurs.

## Non vérifié
- Les écrans n'ont pas été vus dans un navigateur : tests bUnit (pages sur données fixes), tests de l'hôte (403, redirections, jeton du créateur transmis au Gateway, sortie, anti-falsification), tests d'intégration du service sur PostgreSQL, test de routes du Gateway. Pas de passage visuel (mise en page, clavier, lecteur d'écran), pas de test de bout en bout Aspire (inscription → Platform → rôle → renouvellement de session).

## Vérification
Creators : 5 tests unitaires et 10 d'intégration nouveaux (403 sans rôle, inscription, versions des CGU, handle pris, profil et publication, abonnés masqués, contenus et conseils cloisonnés entre créateurs, suspension, fondateur). Gateway : 1 test de routes. Web.Studio : 22 tests (16 bUnit, 6 hôte). Architecture : le Studio et les apps ne référencent aucun SDK Meta, Google ni TikTok.
