# ADR-0012 — Service Insights : événements d'usage, consentement, partitions, KPI, et client analytics (T-801, T-802, T-619)

- Statut : accepté. Hors périmètre : statistiques créateur (`CreatorEngagementAggregatedV1`, `CreatorPlaceLinkChangedV1`, T-1212), orchestration Platform de la suppression et de l'export (T-507), écran des réglages et consentement dans l'app (T-618), métriques OpenTelemetry `onvoyage.app.crashes` / `.audio_failures` / `.gps_losses`.

## Service Insights (`src/Services/Insights`)
- Schéma `insights` : `event` (**partitionnée par mois** sur `occurred_at`), `consent_projection`, `daily_kpi`, `config_snapshot`. Aucune colonne de position (test sur le schéma de la base).
- `POST /api/insights/v1/events` (voyageur) : lot idempotent, validé contre le catalogue §17.3 partagé avec l'app (`OnVoyage.Insights.Contracts/EventCatalogue`). Un événement inconnu, une propriété hors catalogue (donc `lat`, `lon`, texte saisi, identifiant d'appareil…), une valeur hors plage ou une plateforme inconnue refuse **tout le lot** (400, Problem Details `validation`) ; rien n'est stocké. Les événements trop anciens pour leur durée de conservation sont ignorés, pas refusés (appareil resté hors ligne).
- **Idempotence** : l'`id` d'événement est choisi par le client ; clé primaire `(id, occurred_at)` (la clé de partition doit en faire partie) et `insert … on conflict do nothing` en une seule instruction par lot. La réponse compte `accepted` / `duplicates` / `ignored`.
- **Consentement (§16.3)** : projection de `ConsentChangedV1` (genre `analytics` seulement ; un changement plus ancien que la ligne stockée est ignoré). Pas de ligne = refusé. Sans consentement, seuls `app_crash`, `audio_error`, `gps_loss` sont conservés ; le reste est compté dans `ignored`.
- **Partitions mensuelles** : la migration crée la table partitionnée (SQL à la main, EF Core ne sait pas déclarer `PARTITION BY RANGE`) et les partitions du mois précédent, courant et des deux suivants. `PartitionCatalog` crée une partition à la demande quand un événement tombe dans un mois sans partition, et la tâche quotidienne garantit les mois à venir.
- **Rétention (⚙️)** : `RunMaintenanceCommand` (tous les jours, `InsightsScheduler`) supprime les partitions entièrement antérieures à `retention.analytics_raw_months` (13), supprime par date le reste du mois le plus ancien, et supprime les événements essentiels de plus de `retention.technical_events_days` (90). `insights.daily_kpi` (anonyme) n'est jamais supprimée. Les valeurs viennent de `config_snapshot` (alimentée par `ConfigChangedV1`), avec les valeurs de l'annexe E tant que Platform n'a rien envoyé.
- **Suppression et export** : `TravelerDeletionRequestedV1` supprime événements et projection, et publie `TravelerDataDeletedV1("insights")` dans la même transaction (outbox) ; répéter la demande est sans effet. `TravelerExportRequestedV1` écrit `exports/<exportId>/insights.json` (événements et consentement du voyageur) et publie `TravelerExportPartReadyV1`. Le répertoire est `Insights:ExportDirectory` (stand-in du bucket privé `exports/`). Les quatre contrats sont dans `OnVoyage.Platform.Contracts`, avec les champs exacts du §13.
- **Files** : Insights écoute la file `insights`. Platform y publie `ConsentChangedV1` (`Messaging:ConsentSubscribers`, défaut `["insights"]`) et `ConfigChangedV1` (`Messaging:ConfigSubscribers` contient maintenant `insights`). Insights publie ses réponses sur la file `platform`.

## KPI (T-802)
- `insights.daily_kpi` stocke des **composantes** (comptes par jour, cohorte et nom), pas des ratios : toute période se somme, puis `KpiCalculator` (Domaine, pur) calcule les indicateurs. `ComputeAsync` supprime et reconstruit les jours demandés en une transaction (verrou consultatif : une seule instance à la fois) ; le planificateur reconstruit les 35 derniers jours toutes les heures (`Insights:Kpi:RecomputeDays`, `Insights:Jobs:KpiMinutes`), ce qui laisse la fenêtre J30 se fermer et rattrape les événements tardifs.
- `GET /api/insights/v1/kpis?from&to&destination&cohort` (admin) renvoie exactement le contrat que lit `Web.Admin` (`KpiReport` : `from`, `to`, `destination`, `cohort`, `values{clé:{value,sample}}`, clés de `KpiCatalog`). Un indicateur sans dénominateur est **absent** (l'écran affiche « pas de donnée »). `GET …/kpis/export` renvoie le CSV des composantes (`date,destination,cohort,metric,value`, culture invariante).
- Définitions : **hypothèse centrale** = taux de clic de la cohorte `personalized` / taux de clic de `control` (échantillon = la plus petite des deux séries d'impressions ; absent si une cohorte est demandée) ; **satisfaction** = `poi_liked / (poi_liked + poi_disliked)` (`poi_meh` ignoré) ; **activation** = installations avec un `audio_started` dans les 7 jours (jour d'installation compris) ; **histoires par session** = `audio_started` / sessions (une session = un `session_id` distinct par jour, avec au moins un événement non essentiel) ; **complétion** = `audio_completed` (≥ 80 %, ou sans pourcentage) / `audio_started` ; **rétention Jn** = installations qui reviennent le jour D+n, comptées une fois D+n terminé ; **taux de clic par tranche de `ProfileDepth`** (0–9, 10–49, ≥ 50) ; **`ProfileDepth` médian à J7** (histogramme, car une médiane ne se somme pas) ; **taux de plantage** = sessions avec `app_crash` / sessions. Là où le cahier dit « Pour vous » (satisfaction, tranches), la cohorte `personalized` est utilisée tant qu'aucune cohorte n'est demandée.
- Preuve : jeu synthétique de 40 voyageurs (20 par cohorte) dont chaque indicateur a une valeur exacte attendue (`InsightsKpiTests`), plus les tests purs de `KpiCalculator`.

## Client (T-619)
- `OnVoyage.App.Core/Analytics` : `AnalyticsQueue` (implémente `IAnalyticsSink`, enregistrée par `AddAppCore` avec `TryAdd`), `AnalyticsConsent` (copie locale du consentement), `IAnalyticsTransport` (port), `IAnalyticsStore` (port, mémoire par défaut). `HttpAnalyticsTransport` (App.Infrastructure) envoie par le Gateway avec `BearerTokenHandler`, comme `HttpDiscoveryClient`.
- Lots de 50, premier envoi 60 s après le premier événement en attente (le minuteur ne repart pas à chaque événement) ou tout de suite si le lot est plein ; hors ligne : attente exponentielle de 30 s à 15 min, mêmes identifiants renvoyés ; un lot refusé pour de bon (4xx hors 401/403/408/429) est abandonné ; file bornée à 1 000 événements.
- **Consentement** : accordé → tout est mis en file ; refusé → seuls les événements essentiels ; **sans choix** → les événements non essentiels sont gardés en mémoire (200 au plus), envoyés si le voyageur accepte, jetés s'il refuse (§16.3) ; refuser retire aussi les événements non essentiels déjà en attente, et l'envoi vérifie le consentement une dernière fois.
- Seuls le catalogue et ses propriétés passent (`EventShaping`) : les propriétés hors catalogue sont supprimées (l'événement reste), les valeurs invalides aussi. L'app émet aujourd'hui `distance_m` et `origin` : ils sont convertis en `distance_bucket_50m` et `trigger` ; les événements inconnus (`audio_speed_changed`) sont ignorés. Session = identifiant aléatoire renouvelé après 30 min d'inactivité ; aucun identifiant d'appareil ni publicitaire.

## Écarts au cahier
- **Taille de lot** : l'API accepte jusqu'à 500 événements (§12.7, `sync.max_events_per_batch` de l'annexe E, lu dans la projection de configuration) ; l'app en envoie 50 (§14.8).
- **`profile_depth`** ajouté au catalogue pour `recommendation_viewed` / `recommendation_clicked` : le KPI stratégique (§26) regroupe le taux de clic par `ProfileDepth`, que seule l'app connaît à cet instant. À confirmer avec le propriétaire du produit.
- **`destination_id` de `daily_kpi` toujours vide** : les événements ne portent pas de destination et Insights n'a pas de projection lieu → destination (T-502). Demander une destination renvoie donc « pas de donnée », pas les chiffres globaux.
- **Cohorte** : lue dans les événements `recommendation_*` du voyageur (propriété `cohort`) ; un voyageur qui n'en a jamais émis est « non assigné » (compté dans les totaux sans filtre).
- **Événements essentiels** : leurs propriétés se réduisent à `code` ; `app_version` et `platform` sont des champs de l'enveloppe, pas des propriétés.
- Retirer le consentement ne supprime pas les événements déjà reçus (suppression de compte ou 13 mois).
- La clé d'idempotence n'est pas rattachée au voyageur (`id` + `occurred_at`) : un identifiant v7 collisionnant avec celui d'un autre voyageur au même instant est négligeable, et la partition impose que la clé contienne le moment.
- Indicateurs de `KpiCatalog` non produits (pas de source dans Insights) : `hidden_gem_listens`, `alternative_clicks`, `inaccurate_reports_per_100`, `latency_p95_ms`, `creators_active`, `places_with_creator_content`.
- Les tâches (partitions et rétention, reconstruction des KPI) tournent dans l'API (`BackgroundService`, `Insights:Jobs:Enabled`), pas dans un worker séparé.

## Non vérifié
- **Bout en bout entre processus** (Platform → file → Insights réels sous Aspire) : seuls les deux bouts sont testés (Platform publie dans la file `insights` ; Insights traite les messages invoqués dans le test). Platform n'a pas encore de gestionnaire pour `TravelerDataDeletedV1` / `TravelerExportPartReadyV1` (T-507) : ces messages attendent dans la file `platform`. Platform ne publie pas encore `TravelerDeletionRequestedV1` / `TravelerExportRequestedV1` vers `insights` (T-507).
- **App** : le code MAUI n'est pas compilé ici ; rien n'appelle encore `AnalyticsConsent.Set` (T-618), donc, par défaut, aucun événement non essentiel ne quitte l'appareil ; pas de `IAnalyticsStore` SQLite (la file ne survit à un redémarrage que si l'hôte en fournit un) ; aucun événement du catalogue autre que ceux de l'audio et du mode découverte n'est encore émis par l'app.
- Le contrat du `GET /kpis` est vérifié par la forme JSON, pas en désérialisant avec les types de `Web.Admin` (depuis l'[ADR-0019](0019-suivi-des-lots-signalements-videos-et-kpi-dans-l-admin.md), les tests de `Web.Admin` désérialisent le `KpiReportDto` d'Insights avec les types de l'admin, et vérifient que le catalogue de l'admin correspond à `KpiCalculator`). Trois indicateurs créateurs s'y ajoutent : `creator_block_ctr`, `creator_follow_rate`, `creator_attributed_installs`.
- Pas de test de charge de la requête de reconstruction des KPI (volumes MVP-0 : quelques milliers de voyageurs).

## Vérification
Insights : 30 tests unitaires (partitions, calcul des KPI, catalogue et validation, consentement, bornes), 13 tests d'intégration sur PostgreSQL (consentement, idempotence, 500/501, partitions, rétention, suppression, export, KPI sur jeu synthétique, filtres, CSV, schéma sans position). App : 15 tests de la file (dont « consentement refusé → seuls les événements essentiels »), 11 du transport HTTP. Platform : 2 tests de routage vers la file `insights`.
